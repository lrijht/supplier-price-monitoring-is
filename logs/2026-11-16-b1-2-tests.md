## Інтерфейс, заданий тестами

Сесія Feature реалізує саме його. Решта — на розсуд реалізації. Інтерфейс Б1.1 (лог

### Розбирачі — `spm.update.parsers`

- `available_parsers() -> Iterable[str]` — назви наявних розбирачів без повторів; серед них
  `table_layout`, `cards_layout`, `list_layout` (значення з прикладів контракту `GET /parsers` і
  сценаріїв П-06, Н-11).
- `parse_page(parser: str, html: str) -> list[item]` — позиції в порядку сторінки. Кожна позиція
  має атрибути `sku`, `name`, `unit` (рядки, як на сторінці, без «Арт.» і зайвих пробілів) і
  `price` — `Decimal` з двома знаками (`Decimal("1250.50")`) або `None` для «ціну уточнюйте».
- Сторінки імітатора: `table_layout` — таблиця («1 250,50 грн»), `cards_layout` — картки
  («18.40 грн», артикул «Арт. БК-01»), `list_layout` — список («64,20 грн»).
- `import spm.app, spm.update.parsers` не завантажує модуля `simulator` (перевірка в окремому
  процесі).

Поведінка на нерозбірній сторінці (BDD-051) — Б2, тут не задана.

### Команда створення облікового запису — `spm.auth.cli`

- Запуск: `python -m spm.auth.cli ЛОГІН РОЛЬ`; роль — `manager` або `admin`. `--help` завершується з
  кодом 0, і в довідці немає `--password` чи `-p`.
- `main(argv: list[str], *, config: Config | None = None, read_password: Callable[[str], str] | None = None) -> int`:
  - без `config` — `load_config(os.environ, Path(".env"))`, як у `create_app`;
  - `read_password(prompt)` — інтерактивне введення пароля, за замовчуванням `getpass.getpass`;
    команда викликає його щонайменше раз (може просити підтвердження — тест на кожен запит дає той
    самий пароль);
  - повертає 0, якщо обліковий запис створено, інакше — ненульовий код; помилка argparse
    (`SystemExit`) теж вважається відмовою;
  - сама створює базу і схему, якщо їх ще немає (`init_database`);
  - відмова — з поясненням у stdout чи stderr; для наявного логіна текст містить слово «існує»;
  - пароль аргументом не передається: `ЛОГІН РОЛЬ ПАРОЛЬ`, `--password …`, `-p …` — відмова, нічого
    не створено.
- Правила (REQ-F-006): логін — `[A-Za-z0-9._-]`, 3…32 символи, унікальний без урахування
  регістру; пароль — не менше 8 символів; невідома роль — відмова.
- Таблиця `accounts` (Б1.1): `login` зберігається як введено, `role` — `manager`/`admin`,
  `password_hash` — хеш із сіллю; пароля у відкритому вигляді в жодному файлі бази немає; однакові
  паролі — різні хеші.

### Сесія і вхід (вебінтерфейс і API)

- Cookie сесії `spm_session`, `SameSite=Lax`, без `Secure` (ЗП-4, HTTPS немає). Сесія одна для
  екранів і API.
- Строк — 8 год від останнього запиту за годинником застосунку (`ManualClock`): 7 год 59 хв —
  діє, рівно 8 год — завершена.
- **Екрани.** `GET /login` — HTML-форма `method="post"` з полями `login` і `password`
  (`type="password"`) і заголовком зі словом «Вхід». `POST /login` (форма) — успіх: 302/303 не на
  `/login`; помилка: не переадресація, та сама форма з текстом «Неправильний логін або пароль».
- Без сесії будь-яка адреса екрана (у тестах `/material-comparisons`, `/suppliers`,
  `/suppliers/new`, `/materials`, `/materials/1/links`, `/unlinked-items`, `/settings`) — 302/303/307
  на `/login`, далі форма входу.
- «Вийти» — форма `method="post"` з `action`, що закінчується на `/logout`, і текстом «Вийти» на
  кожному екрані. `POST /logout` — 302/303 на `/login`. Вихід одного клієнта не завершує сесій
  інших.
- **API.** `POST /api/v1/sessions` (JSON `login`, `password`) — 201,
  `{"account": {"login": <як збережено>, "role": …}}`, `Location: /api/v1/sessions/current`,
  `Set-Cookie` з `spm_session` і `SameSite=Lax`. Помилки — `invalid_credentials` (401), 422
  `required`/`unknown_field`/`invalid_type`, 415, 422 `malformed_json` (і для порожнього тіла).
  `GET /api/v1/sessions/current` — 200 `{"account": …}`; `DELETE` — 204 без тіла.
- Без сесії API — 401 `unauthenticated` без заголовка `Location`; 405 на адресах сесій (`detail`
  містить назву методу).
- Немає адрес `/register`, `/signup`, `/accounts`, `/users` ні в API (404 `not_found`), ні на
  екранах (404 або 405).

### Екрани (вебінтерфейс, Jinja2, REQ-NF-015)

Адреси екранів повторюють шляхи API без `/api/v1`. Форми надсилають
`application/x-www-form-urlencoded`; успішна дія — 302/303; відхилена — не переадресація, сторінка
з повідомленням. Менеджер на адміністративних екранах і діях — **403** зі сторінкою «немає доступу»
без даних.

| Адреса | Що |
|---|---|
| `GET /suppliers?page=N` | екран «постачальники» |
| `GET /suppliers/new`, `POST /suppliers` | форма і створення; поля `name`, `catalog_url`, `parser` (`<select>`), `active` (прапорець: є поле — `true`, немає — `false`) |
| `GET /suppliers/{id}`, `POST /suppliers/{id}` | форма редагування і збереження (зокрема деактивація й активація); ті самі поля |
| `GET /materials?page=N` | екран «матеріали» |
| `GET /materials/new`, `POST /materials`; `GET /materials/{id}`, `POST /materials/{id}` | створення і редагування; поля `name`, `unit`, `active` |
| `GET /materials/{id}/links?page=N` | перелік прив'язаних позицій матеріалу (REQ-F-069) з діями «зняти» і «перев'язати» |
| `GET /unlinked-items?page=N&q=…` | список непов'язаних позицій з пошуком |
| `GET /supplier-items/{id}/link?q=…` | вибір матеріалу для прив'язки чи перев'язки з пошуком за найменуванням |
| `POST /supplier-items/{id}/link` | прив'язати чи перев'язати; поле `material_id` |
| `POST /supplier-items/{id}/unlink` | зняти прив'язку |
| `GET /settings`, `POST /settings` | екран налаштувань; поля `update_time`, `notification_threshold` |

- **Таблиця даних.** На екрані-списку рівно одна `<table>` з `<thead>`. Колонки — непорожні `<th>`
  у `<thead>`; колонка дій, якщо є, має порожній `<th>`. Рядок — `<tr>` у `<tbody>`, спершу
  комірки даних. Заголовки звіряються без регістру і лапок «»:
  - «постачальники» — рівно `назва`, `адреса каталогу`, `розбирач`, `активний`,
    `дата останнього оновлення`; дата постачальника без оновлень — «ще не оновлювався»;
    комірки «активний» для активного й неактивного різні;
  - «матеріали» — рівно `найменування`, `одиниця`, `активний`, `кількість прив'язаних позицій`
    (апостроф будь-який);
  - непов'язані позиції — 5 колонок, що починаються з `постачальник`, `артикул`, `найменування`,
    `одиниця`, `дата`; дата — РРРР-ММ-ДД;
  - перелік прив'язаних позицій — рівно `постачальник`, `артикул`, `найменування`, `одиниця`; у
    тексті сторінки є «зняти» і «перев'язати».
- По 50 рядків, сторінка — параметр `page`; перша сторінка має посилання з `page=2`.
- Порядок — П-3/П-4 (як у API). Вибір матеріалу: найменування в тексті сторінки йдуть в абетковому
  порядку; `q` фільтрує без урахування регістру.
- Розбирач на формах постачальника — лише `<select name="parser">`, варіанти (`value`) — рівно
  `GET /api/v1/parsers`; поля `<input name="parser">` немає.
- На сторінках і формах постачальників і матеріалів немає слів «видалити», «вилучити».
  `DELETE /suppliers/{id}`, `POST /suppliers/{id}/delete` (так само для матеріалів) — 404 або 405,
  запис лишається.
- **Тексти відмов** — `detail` відповідних кодів контракту (`docs/api/resources.md`, розділ 4).
  Тести шукають фрагменти: «обов'язков», «уже є», «http або https», «немає в списку наявних»,
  «одиницю не можна змінити: є ціни або прив'язки», обидві одиниці, артикул уже прив'язаної
  позиції, найменування матеріалу й «активуйте», «від 0,1 до 50», «ГГ:ХХ».
- **Налаштування.** Поточні значення видно в тексті сторінки або як `value` полів
  `update_time`/`notification_threshold`. Поріг показується з комою: «0,5» (поле) чи «0,5 %»
  (текст); 1 % — «1»; «0.5» не показується. Форма приймає «0.5» і «0,5»; відхилена форма не
  зберігає жодного значення.

## Перевірка самих тестів

У червоному прогоні майже всі нові тести падають на фікстурах, тож помилок у самих перевірках не
видно. Тому окремий агент написав у тимчасовому каталозі сесії (поза репозиторієм) одноразовий
прототип `spm` за інтерфейсом вище і прогнав на ньому весь набір через `PYTHONPATH`. Код
репозиторію при цьому не змінювався.

Перший прогін: 471 passed, 3 failed. Знайдено три помилки в тестах, усі виправлено:

| Тест | Помилка | Виправлення |

## Рішення, які агент ухвалив сам

Людині варто їх перевірити на TEST-GATE Б1.

**Інтерфейс:**
- адреси екранів повторюють шляхи API без `/api/v1`; форми редагування — `POST` на адресу запису
  (HTML-форма не надсилає `PATCH`); зняття прив'язки — `POST …/unlink`;
- прапорець `active` у формах: немає поля — `false`;
- назви розбирачів `table_layout`, `cards_layout`, `list_layout` — з прикладів контракту;
- коди подій журналу, назви дій, `object_type`, `entered_login`, `account_login`, `account_role`,
  `reason_code`, значення `result` (`success`/`rejected`) — за таблицею вище;
- команда: модуль `spm.auth.cli`, аргументи `ЛОГІН РОЛЬ`, ролі англійською, як у даних;
- позиції в тестах — функцією `spm.storage.add_supplier_item`, а не SQL у тестах, щоб тести не
  залежали від схеми позицій.

**Перевірки:**
- менеджер на адміністративних екранах і формах — статус 403 (REQ-F-005 вимагає сторінку
  «немає доступу», статус не задано; 403 — як в API);
- тексти відмов на екранах — `detail` контракту; тести шукають короткі фрагменти;
- сесія завершена рівно через 8 год (не «понад 8 год»);
- вихід не завершує інших сесій того самого користувача;
- пароль чутливий до регістру; логін «Admin » з пробілом тести не перевіряють;
- порожнє тіло JSON — `malformed_json`;
- «штучний збій сховища» REQ-NF-018 — `DROP TABLE accounts`; реалізація з постійним з'єднанням теж
  побачить збій;
- REQ-NF-033 для вебінтерфейсу звіряє видимий текст сторінки після переадресації.
