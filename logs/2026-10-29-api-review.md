## 4. Поведінка, якої немає в SRS 1.9

Нових функцій користувача контракт не додає: кожна операція відповідає екрану чи дії REQ-F-001…REQ-F-069
або REQ-F-070, REQ-F-071; облікових записів API не створює, операцій видалення немає (DELETE — лише
вихід і зняття прив'язки). Те, чого SRS не задає:

- розширена видимість даних для менеджера через списки REQ-F-070 — РА-12;
- правила протоколу (415, 422 для невідомих полів, сторінка за межами, фільтри з неіснуючим
  ідентифікатором, ідемпотентний `PUT`, 200 для ручного запуску без постачальників) — РА-13;
- машинна класифікація причин помилки `reason_code` і видів попереджень `warnings[].kind` —
  відповідає переліку Д.8, нового не вводить;
- порядок `supplier_run_statuses` за назвою постачальника (уточнення №12) — SRS порядку рядків у
  записі журналу не задає; відповідає загальному правилу REQ-F-057 для списків постачальників.

Суперечності з п. 2.7 SRS (те, чого немає в поточній версії) не знайдено: ключів, токенів,
вебхуків, експорту, видалення, керування користувачами в контракті немає.

## 5. Розбіжності `openapi.yaml` і `resources.md`

Механічна звірка таблиці операцій (розділ 3 `resources.md`) з контрактом за REQ-ID, BDD і кодами
HTTP розбіжностей не дала (28 з 28). Поля розділу 2.1, коди розділу 4, значення переліків
(ПА-5) і формати (ПА-6…ПА-8) у контракті збігаються з документом.

Розбіжності за формою:
