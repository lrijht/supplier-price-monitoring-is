## Інтерфейс, заданий тестами

Сесія Feature реалізує саме його; решта — на розсуд реалізації. Інтерфейс Б1
(`2026-11-16-b1-1-tests.md`, `2026-11-16-b1-2-tests.md`) не змінюється, нижче лише додане.

### Запуск з коду — `app.state.updates`

`create_app(config, *, clock)` кладе в `app.state.updates` об'єкт пакета `spm.update`, що реалізує
порт «запустити оновлення» з `services` (`docs/architecture.md`, розділ 5). Схема бази має існувати
(тести спершу відкривають клієнт, тобто проходить старт застосунку). Методи — синхронні, у потоці
виклику, час — `clock.now()`:

- `run(trigger: str, *, started_by: str | None = None) -> int | None` — виконує один запуск зараз і
  повертає його id. `trigger`: `"scheduled"`, `"manual"`, `"catch_up"` (значення API); для
  `"manual"` — `started_by` (логін). Без активних постачальників запуску немає, журнал оновлень
  отримує запис `no_active_suppliers` з приводом `scheduled` чи `manual`, повертається `None`. Обмежень
  розкладу `run` не перевіряє: це «сам запуск».
- `tick() -> int | None` — одна перевірка планувальника в момент годинника: якщо настав
  налаштований час цієї доби за Києвом (REQ-F-018, REQ-F-054, REQ-F-055) і запуску за розкладом цієї
  доби ще не зараховано — запис «пропущено» (якщо триває інший запуск, REQ-F-022), запис «немає
  активних постачальників» або запуск за розкладом; повертає id запуску або `None`. Тест кличе
  `tick()` у ті моменти, коли робочий планувальник перевіряв би годинник.
- `startup() -> int | None` — те, що система робить одразу після старту: запуски, що лишилися
  `in_progress`, стають `interrupted` (постачальник без записаних даних — `not_finished`), далі,
  якщо виконано умову REQ-F-023, — один запуск `catch_up`; повертає його id або `None`.

Постачальники в запуску обробляються **по одному в порядку назви** (як `supplier_run_statuses`,
REQ-F-057): дані постачальника записано до того, як іде запит до наступного. Це потрібно тестам
«триває» і «перервано» (BDD-069, BDD-039, BDD-066).

### Ручний запуск і фоновий режим

- `POST /api/v1/runs` і форма `POST /runs` повертають відповідь одразу після початку запуску;
  запуск іде у фоновому потоці того самого процесу (тест чекає його завершення опитуванням
  `GET /api/v1/runs/{id}`). Ознака «триває» спільна для `run`, `tick` і ручного запуску одного
  застосунку.
- `create_app(config, *, clock, background_updates: bool = False)` — новий необов'язковий параметр.
  Без нього (як в усіх тестах Б1) нічого не запускається само: ні доганяння, ні планувальник. З
  `background_updates=True` під час старту застосунку у фоні виконується `startup()`, а потік
  планувальника викликає `tick()` **не рідше разу на секунду**; під час зупинки застосунку потік
  завершується. Команда запуску системи (одна команда, REQ-NF-014, T-25) має вмикати цей режим;
  саму команду тести не задають.

### Отримання сторінки — `spm.update.fetch`

- Іменована константа `FETCH_TIMEOUT_SECONDS = 30`; код читає її як атрибут модуля в момент запиту,
  тож тест підміняє її `monkeypatch.setattr(spm.update.fetch, "FETCH_TIMEOUT_SECONDS", 1)`, і
  причина помилки — «перевищено час очікування 1 с».
- Одна спроба на постачальника за запуск, без повторів. Відповідь не 2xx або відмова з'єднання —
  «сторінка недоступна» (`unavailable`); у тестах — режим імітатора «недоступний» (503).

### Збережені дані для тестів — `spm.storage`

Екранів історії і стрічки ще немає (Б3), тому ціни дня й події тести читають зі сховища, як
`add_supplier_item` у Б1.2:

- `daily_prices(database_path) -> Iterable[row]` — усі ціни дня; атрибути: `supplier_item_id`,
  `material_id`, `price_date` (`date`), `price` (`Decimal`, два знаки), `unit` (рядок зі сторінки),
  `unit_mismatch` (`bool`).
- `events(database_path) -> Iterable[row]` — усі події **в порядку створення**; атрибути: `kind`
  (`price_change`, `appeared`, `disappeared`), `event_date` (`date` — дата запуску),
  `created_at` (`datetime` зі зсувом київського часу), `material_id`, `supplier_id`,
  `supplier_item_id`, `old_price`, `new_price` (`Decimal` або `None`), `change_percent` (число,
  округлене до 0,1, половина від нуля, або `None`), `price` (`Decimal` або `None`). Поля, яких вид
  події не має, — `None`.
- Таблиця цін дня — `daily_prices` з колонкою `supplier_item_id`: тест REQ-NF-016 «штучно викликає
  збій посеред запису» тригером SQLite на вставку в неї (як `DROP TABLE accounts` у Б1.2).

### Екрани

Адреси повторюють шляхи API без `/api/v1`, як у Б1.

| Адреса | Хто | Що |
|---|---|---|
| `GET /run-log-entries?page=N` | адмін; менеджер — 403 «немає доступу» | журнал оновлень, 50 записів на сторінку, від новіших |
| `POST /runs` (форма без полів) | адмін; менеджер — 403, запуску немає | кнопка ручного запуску; успіх — 302/303 (на журнал); «немає активних постачальників» — після переходу сторінка з цим текстом; під час іншого запуску — не переадресація, сторінка з «оновлення вже триває» |
| `POST /volume-acceptances` (поля `run_id`, `supplier_id`) | адмін; менеджер — 403, обсяг не прийнято | кнопка «прийняти новий обсяг»; успіх — 302/303 |
| `GET /supplier-update-statuses?page=N` | обидві ролі | стан оновлення постачальників |

- **Журнал оновлень.** На сторінці одна таблиця даних (`<table>` з `<thead>`, як у Б1). Кожен
  постачальник кожного запуску — рядок `<tr>`, серед комірок якого є назва постачальника, статус
  («успіх», «частково», «помилка», «не завершено») або «—», кількість розібраних позицій або «—»,
  текст помилки чи попередження (попередження містить артикул). Запис без постачальників («немає
  активних постачальників», «пропущено», прийняття обсягу) — один рядок. Решту полів запуску тести
  шукають у тексті сторінки: дата РРРР-ММ-ДД, час ГГ:ХХ:СС (початок і завершення; «—» для
  незавершеного), «за розкладом» / «вручну» / «доганяння», логін для ручного, «успіх» / «частково» /
  «помилка» / «перервано» / «триває»; для прийняття — логін, час ГГ:ХХ:СС і прийнята кількість.
  Кнопка ручного запуску — форма `method="post"` з `action`, що закінчується на `/runs`. Кнопка
  «прийняти новий обсяг» — форма `method="post"` з `action` на `/volume-acceptances` і полями
  (`<input>`, зокрема прихованими) `run_id` і `supplier_id`; у тексті сторінки є «прийняти новий
  обсяг». На сторінці немає слів «видалити», «вилучити».
- **Стан оновлення постачальників.** Таблиця даних з колонками рівно «постачальник», «дата останнього
  оновлення»; лише активні постачальники; дата РРРР-ММ-ДД або «ще не оновлювався»; порядок і сторінки
  — як у «постачальники» (П-3/П-4).

### API (операції 22, 25–28)

За контрактом. Тести додатково фіксують:
- `POST /runs`: тіло 202 — запуск, як `GET /runs/{id}` у ту мить; `started_at` — момент годинника;
  `Location: /api/v1/runs/{id}`; без активних постачальників — 200 без `Location`; `Content-Type` не
  потрібен.
- `GET /runs/abc` — 422 `invalid_type` для `run_id`; неіснуючий — 404; менеджеру — 403 і для
  неіснуючого.
- `POST /volume-acceptances`: тіло без полів — 422 `required` для обох; неіснуючі `run_id` чи
  `supplier_id` — 422 `reference_not_found` для того поля; невідоме поле — `unknown_field`; рядок замість
  числа — `invalid_type`; 409 — коли постачальник у запуску не «частково» або запуск не останній для
  нього; у відповіді 201 немає `Location`.
- `DELETE` на `/run-log-entries` і `/runs/{id}` — 405 `method_not_allowed` (REQ-NF-019).
- `trigger` запису журналу — лише для `no_active_suppliers`, для `run` — `null`.

### Журнал дій і технічний журнал (події Б2)

Загальні поля — як у Б1. `request_id` порівнюється як рядок: `str(request_id) == str(id)`.

| `event` | Коли | Поля події | `request_id` |
|---|---|---|---|
| `manual_run` (дія) | ручний запуск через API чи форму; `result` `success` або `rejected` з `reason_code` `run_in_progress` | `object_type` `run`, `object_id` — id запуску (`null`, якщо запуску немає) | HTTP-запиту |
| `volume_accept` (дія) | прийняття обсягу; `rejected` з `volume_acceptance_unavailable` | `object_type` `volume_acceptance`, `object_id` — id прийняття (`null` для відхиленого) | HTTP-запиту |
| `access_denied` | 403 менеджеру | `action` `manual_run` (`object_type` `run`) або `volume_accept` (`volume_acceptance`) | HTTP-запиту |
| `run_started` | початок запуску | `run_id`, `trigger` | ручний — запиту, що почав; за розкладом і доганяння — id запуску |
| `supplier_status` | дані постачальника записано (або «помилка») | `run_id`, `supplier_id`, `status`, `parsed_items_count` (значення API) | як `run_started` |
| `run_finished` | завершення | `run_id`, `status` (`success`, `partial`, `error`) | як `run_started` |
| `run_interrupted` | старт системи позначив запуск перерваним | `run_id` | не перевіряється |
| `run_skipped` | запис «пропущено» | `run_log_entry_id` | `run_log_entry_id` |
| `no_active_suppliers` | запис «немає активних постачальників» | `run_log_entry_id`, `trigger` (`scheduled`/`manual`) | `run_log_entry_id` |

- Технічний журнал: помилка отримання чи розбору сторінки постачальника — запис із загальними полями і
  полями `run_id`, `supplier_id`, `error` (непорожній опис). `request_id` — як у записів того самого
  запуску в журналі дій. Код події тести не задають.
- REQ-NF-033: шлях технічного журналу чи журналу дій — каталог; ручний запуск усе одно 202 з тим
  самим тілом, і запуск завершується як без збою.

### Інфраструктура тестів (не інтерфейс системи)

- Фікстура `sim` запускає справжній імітатор (`simulator.create_app`) на 127.0.0.1 в обгортці ASGI,
  яка рахує запити за шляхом і може притримати відповідь каталогу до `release()` — так запуск
  «зупиняється» посередині без реального очікування. Дані — файл даних імітатора (REQ-NF-027);
  аномалії сторінки (повторний артикул, рядок без артикула — `sku: ""`, нерозбірна ціна, ціна 0 і
  від'ємна) задаються самим файлом даних.
- «Зупинка процесу» — `tests/update_worker.py`: окремий процес Python із тим самим `spm`, базою і
  журналами та `ManualClock` у заданий момент виконує `app.state.updates.run(...)`; тест чекає, поки
  запуск дійде до притриманої сторінки (і, якщо треба, поки дані попереднього постачальника
  записано), і вбиває процес. «Старт системи» — новий `create_app` на тих самих даних і
  `app.state.updates.startup()`.
- `keep_sessions` (усі модулі Б2, через `pytestmark`): тести переводять керований годинник на дні
  вперед, а сесія завершується після 8 год бездіяльності (REQ-NF-021). Після кожного руху годинника
  кожен клієнт тесту із сесією (`admin_client`, `manager_client`, клієнти `restart`) входить знову
  через `POST /api/v1/sessions`. Внутрішніх імен `spm` фікстура не використовує.

## Перевірка самих тестів

Як у Б1.2: окремий агент написав у тимчасовому каталозі сесії (поза репозиторієм) одноразовий
прототип Б2 за інтерфейсом вище (копія репозиторію; код Б2 лише в копії `src/spm`, тести копії —
байт у байт як у репозиторії) і прогнав на ньому весь набір. У репозиторії `src/` і `simulator/` не
змінювалися; прототип лишився лише в тимчасовому каталозі.

Перший прогін: 128 із 186 тестів Б2 падали з однієї причини — помилки в тестах (таблиця нижче).
Після виправлень: **186 passed** за 4 хв 16 с на прототипі, без нестабільних тестів (перевірено
тричі, зокрема під навантаженням); функціональні тести Б1 на прототипі зелені. Тестів, довших за
3 с, немає: найдовші ~1,5 с (120 записів журналу, тести із зупинкою процесу).

Неоднозначності, які прототип вирішив сам і які тести **не** перевіряють (рішення — за сесією
Feature або людиною):
- точне вікно `tick()` (тести викликають його рівно в налаштований час);
- як планувальник дізнається про зміну часу на вже минулий (тести вимагають лише результату);
- привід запису «немає активних постачальників», якщо його дало доганяння;
- `run()` під час іншого запуску;
- повторне прийняття вже прийнятого обсягу;
- попередження «одиниця не збігається» для позиції без ціни;
- `request_id` запису `run_interrupted`;
- порядок записів журналу з однаковим часом (тести не ставлять таких записів поруч).

Розбирачам Б1 треба розрізняти рядок без артикула чи з нерозбірною ціною (пропуск із
попередженням) і «ціну уточнюйте» (ціни немає). Прототип додав для цього окрему функцію поруч із
`parse_page`; тести задають це лише через запуск.

## Рішення, які агент ухвалив сам

Людині варто їх перевірити на TEST-GATE Б2.

- Порт запуску — `app.state.updates` з методами `run`, `tick`, `startup`. Планувальник у тестах —
  виклики `tick()` у потрібні моменти; у роботі — потік із `background_updates=True` (REQ-NF-014
  перевірено саме з ним).
- Постачальники обробляються по одному в порядку назви. SRS порядку обробки не задає; це потрібно для
  тестів «триває» і «перервано».
- «Зупинка процесу» — справжнє вбивство окремого процесу (`tests/update_worker.py`), а не стан,
  записаний прямо в сховище. T-20 дозволяв обидва способи; так тест не залежить від схеми.
- Ціни дня й події тести читають через `spm.storage.daily_prices` і `spm.storage.events`: екранів Б3
  ще немає. Для REQ-NF-016 — тригер SQLite на таблицю `daily_prices` (назва таблиці стає частиною
  інтерфейсу).
- Коди подій журналу дій для запусків і дій та їхні поля — таблиця в розділі «Інтерфейс».
  `request_id` записів «пропущено» і «немає активних постачальників» звіряється з полем
  `run_log_entry_id`: в API записи журналу оновлень id не мають.
- Екрани: адреси як в API, у журналі — рядок на кожного постачальника запуску, менеджерові — 403.
- Весняний перехід на літній час — 2027-03-28, бо керований годинник іде лише вперед від 2026-07-15;
  осінній — 2026-10-25.
