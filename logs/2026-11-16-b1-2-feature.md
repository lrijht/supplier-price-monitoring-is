## Рішення, які агент ухвалив сам

Людині варто їх перевірити.

**Архітектура.**
- Параметри шляху, запиту й тіло API читаються вручну, а не автоматичним розбором FastAPI: інакше
  FastAPI відповідав би 422 до перевірки сесії, а контракт вимагає 401 → 403 → 422 → 404 → 415 →
  422 → 409.
- Список розбирачів `services` отримує від `create_app` параметром (`available_parsers` з
  `update`), тож `services` не залежить від `update`. Порт запуску оновлення не оголошено — у Б1.2
  він не потрібен.
- `services` повертає рядки `storage` як свої моделі читання (`Material = MaterialRow`,
  `SupplierItem = SupplierItemRow`), щоб `api` і `web` не імпортували `storage`.
- Логін і роль запису `http_request` передаються через змінну контексту з тримачем (`dict`): сесію
  визначає `auth` усередині запиту, а запис пише middleware після відповіді.
- Команда створення облікового запису читає конфігурацію сама (`load_config`), бо це окрема точка
  входу, не застосунок; так задав інтерфейс тестів.
- Сортування й пошук — у Python: SQLite не вміє порядку П-3 і регістру кирилиці. Для навчального
  обсягу (сотні записів) цього досить.

**Сесії й вхід.**
- Cookie — випадковий токен із підписом HMAC секретом сесії; у базі — лише SHA-256 токена. Ні
  значення cookie, ні пароля в базі й журналах немає.
- Сесія, що завершилася (≥ 8 год), видаляється тим запитом, який це виявив; він пише
  `session_expired`.
- Запис `http_request` успішного входу має логін і роль щойно відкритої сесії (запит прийшов без
  сесії, але закінчився з нею).
- Після входу формою — переадресація на `/` (головна з навігацією за роллю); невдалий вхід формою —
  статус 401 з тією самою формою.
- Без сесії будь-яка адреса поза `/api/v1`, якої немає (зокрема `/material-comparisons`), веде на
  форму входу; із сесією — сторінка «не знайдено» 404.

**Журнал дій.**
- `access_denied.action` для операцій читання — назви агента: `supplier_list`, `supplier_read`,
  `parser_list`, `material_list`, `material_read`, `material_links_read`, `unlinked_items_read`,
  `settings_read`; для форми вибору матеріалу — `link_create`. Для `PATCH` менеджера — завжди
  `…_update` (тіло до перевірки ролі не читається).
- «Відхилено» пишеться для 422 тіла (зокрема `malformed_json`, `unknown_field`, `invalid_type`) і
  409; для 404 і 415 запису дії немає — дії над об'єктом не відбулося.
- `PUT …/link` з тим самим матеріалом — 200 без запису: стан не змінився. Відхилена прив'язка —
  `link_change`, якщо позиція вже прив'язана, інакше `link_create`.
- `PATCH`, що змінює `active` разом з іншими полями, — `…_deactivate` / `…_activate`.
- Рівень: дія «успіх» — `info`, «відхилено» і `access_denied` — `warning`.

**Інше.**
- `total_pages` для порожнього списку — 0 (контракт дозволяє `minimum: 0`).
- Конфлікти 409 перевіряються в порядку: `material_inactive` → `link_units_differ` →
  `material_supplier_already_linked` (контракт порядку не задає).
- Вибір матеріалу показує й деактивовані матеріали з позначкою «деактивовано»; спроба прив'язки
  відхиляється за REQ-F-050 з поясненням.
- Відхилена форма — статус 422 (правила введення) або 409 (стан) і та сама форма з причиною.
- Хибний `page` на екрані — перша сторінка (у API — 422 `page_invalid`).
- Кирилиця поза українською абеткою (ы, ё, …) — після української абетки за кодом символу; SRS
  такого випадку не задає.
- Назви, адреси й одиниці зберігаються з обрізаними пробілами на краях.

### Що незвичне

1. **Пароль через stdin, а не `getpass`.** Контрольний запуск не пройшов інтерактивного введення
   пароля в консолі Windows; перевірено ту саму `main()` з іншим джерелом пароля. Варто один раз
   запустити `python -m spm.auth.cli ЛОГІН РОЛЬ` у справжньому терміналі.
2. **Тривалість входу ~135 мс** (`duration_ms` 137, 136, 133) проти 3–9 мс інших запитів — це
   scrypt; невдалий вхід триває так само, тож час не видає, чи існує логін.
3. **Запис дії йде перед записом `http_request`** того самого запиту: `http_request` пишеться після
   відповіді. Порядок рядків — не порядок початку запитів.
4. **`http_request` входу має логін**, хоча запит прийшов без сесії (див. рішення вище).
5. **uvicorn не надрукував рядків зупинки:** `kill` з Git Bash завершує процес Windows одразу, без
   `lifespan` shutdown. На застосунок не впливає (стану під час зупинки він не пише).
6. Запис готовності сервера (`GET /login`) — від перевірки агента, не від сценарію.
7. Консоль uvicorn з `--no-access-log` — лише 4 рядки старту, рядків запитів немає.

`var/b1-2-control/` лишився на диску з журналами й базою контрольного запуску; `var/` — у
`.gitignore`, в індекс не потрапляє.

- **Пакування шаблонів.** `src/spm/web/templates/*.html` читаються з каталогу пакета. У `.venv`
  пакет встановлено в редагованому режимі, тож усе працює. Для звичайного встановлення
  (`pip install .`) потрібно додати шаблони в дані пакета (`[tool.setuptools.package-data]` у
  `pyproject.toml`) — окремим комітом `chore:`, за рішенням людини.
- **Б2:** дата останнього оновлення постачальника (зараз завжди «ще не оновлювався»), ціни дня в
  перевірці одиниці матеріалу (REQ-F-009), записи запусків у журнал дій, нерозбірна сторінка
  (BDD-051), порт запуску оновлення в `services`.
- **Б3:** позначка «постачальник неактивний» на екрані непов'язаних позицій (REQ-F-011, T-42),
  екрани менеджера і склад меню за ролями (REQ-NF-003), операція 15 і екран «позиції, що
  потребують уваги».
- Тривалість прогону тестів (~3 хв) — через scrypt у фікстурах; якщо заважатиме, можна обговорити
  параметри хешу для тестів (це зміна інтерфейсу, тож — рішення людини).
