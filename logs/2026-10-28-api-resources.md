# 2026-10-28 — Сесія агента: ресурси REST API (Лаб. 4, крок 2)

**Задача:** спроєктувати REST API на рівні ресурсів за SRS 1.8 (адендум A-03, Р-117), ще без
`spec/openapi.yaml`. Гілка `agent/api-resources`. Код у `/src` не писали.

## Промпт (суть)

- `docs/api/resources.md` українською:
  1. таблиця всіх REQ-F: операція API чи внутрішня поведінка і чому;
  2. модель ресурсів: ресурс, термін глосарію, URI, поля, зв'язки; діаграма в
     `docs/api/resources.mmd` (Mermaid classDiagram);
  3. таблиця операцій — заготовка трасування «REQ → API»;
  4. чернетка моделі помилок (`application/problem+json`, RFC 9457, поля `type`, `title`,
     `status`, `detail`, `code`, `errors`) з таблицею кодів;
  5. «Прогалини» — питання з варіантами, без рішень агента.
- Правила:
  - шляхи множиною в kebab-case, поля в snake_case, назви лише з глосарію;
  - без дієслів в адресах: ручний запуск — `POST /runs`, прийняття обсягу — на розсуд агента з
    поясненням;
  - DELETE ніде немає, деактивація через `PATCH active=false`;
  - сторінки по 50 з параметром `page`;
  - без деталей реалізації;
  - вхід і вихід через ресурс сесії, облікових записів в API немає.
- Якщо правило суперечить SRS — зупинитися. `openapi.yaml` не робити. Docs-файли — в індекс, лог —
  ні, не комітити.

## Перевірка правил проєктування на суперечність із SRS

Прямих суперечностей із SRS 1.8 агент не знайшов, тому роботу не зупиняв.

- «DELETE нема ніде» суворіше за SRS. REQ-F-010 і REQ-NF-031 забороняють видаляти записи, але
  REQ-F-010 прямо каже, що зняття прив'язки — не видалення, а сесія — не запис. SRS не вимагає
  DELETE, тож суперечності немає. Проте для зняття прив'язки (ПА-1) і виходу (ПА-2) правило лишає
  лише незвичні для REST способи. Обидва питання винесено людині з варіантами.
- «Назви лише з глосарію» конфліктує з «вхід/вихід через ресурс сесії»: терміна «сесія» в глосарії
  немає (ПА-3). Ресурс названо `sessions` за промптом.
- Розбиття по 50 узгоджується з REQ-F-057. Агент застосував його лише до списків, які називає
  REQ-F-057, а таблиці порівняння, історії й деталі запуску не розбиваються.

## Що зробив агент

- **Розділ 1.** 69 REQ-F:
  - 33 — операції API, з них REQ-F-049 і REQ-F-063 мають і внутрішню частину;
  - 35 — внутрішня поведінка з указаними операціями, де видно результат;
  - 1 — поза API (REQ-F-006).

  Скрипт перевірив, що всі 69 ID є рівно один раз, а кожен REQ і BDD, на який посилається
  документ, існує в SRS.
- **Розділ 2.** 20 ресурсів, кожен прив'язано до терміна глосарію. Вкладені ресурси власних адрес
  не мають: обліковий запис, позиція постачальника, ціна дня, статус постачальника в запуску.
  Пояснено вибір:
  - `POST /volume-acceptances` з `{run_id, supplier_id}` — прийняття є записом журналу (Д.7а);
    `run_id` дає 409, якщо запуск уже не останній (REQ-F-031). Відкинуто PATCH бази обсягу —
    це була б нова функція;
  - `/links` з окремими POST (прив'язка, 409 для вже прив'язаної позиції, REQ-F-013) і PATCH
    (перев'язка);
  - окремі колекції `/unlinked-items` і `/attention-items`;
  - `/events` як стрічка;
  - без колекції цін дня.
- **Розділ 3.** 28 операцій із роллю, параметрами, тілом, відповіддю, кодами, REQ і BDD. BDD взято
  з `spec/traceability.md`. Окремо перевірено, що кожен з 11 екранів REQ-NF-003 має операцію.
  Без операції лишилися лише списки вибору для менеджера (ПА-14).
- **Розділ 4.** Модель помилок і 18 кодів верхнього рівня, 8 кодів полів для `errors`. Тексти
  detail узято з SRS лише там, де SRS дає їх дослівно:
  - «немає доступу»;
  - «одиницю не можна змінити: є ціни або прив'язки»;
  - «оновлення вже триває»;
  - «матеріал деактивовано»;
  - «немає активних постачальників».

  Для REQ-F-014, REQ-F-048 і REQ-F-050 записано лише вимогу SRS до змісту тексту.
- **Розділ 5.** 23 прогалини ПА-1…ПА-23. Префікс «ПА» обрано, щоб не плутати з П-1…П-8 у
  `docs/tickets.md`.
- **Діаграма.** Mermaid CLI в оточенні немає, тож рендер діаграми агент не перевірив. Синтаксис
  обрано консервативний: підписи класів у лапках, прості анотації `<<resource>>` і `<<embedded>>`.

## Рішення агента в межах правил (на перевірку людині)

- Порядок перевірок 401 → 403 → 404 → 422 → 409: тоді менеджер на адміністративній адресі отримує
  «немає доступу», а не «не знайдено» (REQ-F-005).
- 422 — запит некоректний сам собою; 409 — суперечить поточному стану системи.
- DELETE відповідає 405: REQ-F-010 вимагає, щоб прямий запит на видалення відхилявся.
- `POST /runs` повертає 202 з `Location` — запуск триває до 5 хвилин (ПА-13).
- Назви полів, яких немає в глосарії, позначено `*` і зібрано в таблицю ПА-4.

## Що агент не вирішував і передає людині

Усі питання розділу 5 `docs/api/resources.md`. Найважливіші для контракту:
- ПА-1 і ПА-2 — зняття прив'язки і вихід без DELETE;
- ПА-4 і ПА-5 — назви полів і значення перелічень;
- ПА-6 — формат чисел;
- ПА-9 — тексти помилок;
- ПА-12 і ПА-13 — відповіді `POST /runs`, зокрема стан запуску, що триває. Такого статусу в
  REQ-F-032 немає;
- ПА-14 — списки вибору для менеджера: без них менеджер через API не відкриє історію
  деактивованого матеріалу (REQ-F-049).
