«публічний програмний інтерфейс (API) для інших систем» не входить (Р-39). Агент працював у гілці

## Що зробив агент

**Генератор матриці.** Генератор із сесії A-02 у репозиторії не зберігся. Агент написав його заново
в тимчасовому каталозі сесії. Колонку «Тікет» (її заповнив T-03, коміт `701c3a8`) генератор бере з
чинної матриці за ID вимоги. Із SRS 1.7 генератор відтворив чинний `spec/traceability.md` байт у
байт (SHA-256 `bb565c4d…2207`). Лише після цього агент перегенерував матрицю з SRS 1.8: 69 REQ-F,
31 REQ-NF, 68 BDD, 16 UC. Діф матриці — рядок «Разом», колонка BDD у REQ-F-003 і REQ-F-005, новий
рядок REQ-NF-031 з порожньою колонкою «Тікет».

У рядку «Разом» генератор узгоджує числівник: «31 нефункціональна», а не «31 нефункціональних».
Для 30 вимог текст той самий, тому перевірка з SRS 1.7 дає той самий результат.

**SRS 1.8.** Змінено шапку, «Історію змін», п. 1.4, 1.5, 2.1, 2.2, 2.4, 2.5, 2.7, 3.1.4, додаток А
(BDD-068 після BDD-031) і додаток В (вступ і рядок Р-117). Агент скриптом перевірив, що колонка
«Вимоги» додатка В.2 для всіх рішень збігається з колонками «Джерело» вимог: Р-117 цитує лише
REQ-NF-031.

**Що ще зачіпає рішення, крім пунктів із промпту** (агент змінив і повідомив людині):
- п. 1.4 — рядки `spec/addendum-A03.md` і `spec/openapi.yaml` (файлу контракту ще немає);
- п. 1.5 — «Р-01…Р-117»;
- п. 2.2 — одне речення: ті самі функції доступні через REST API (REQ-NF-031);
- п. 2.4 — «доступ через вебінтерфейс у браузері (задум, «Де») і через REST API (Р-117)»;
- п. 2.7 — до рядка про ключі й токени дописано вебхуки: за Р-117 вони теж лишаються поза межами.

**Глосарій:**

- нові терміни «REST API», «Контракт API», «Модель помилок API» (розділ «Система та її оточення») і
  «Обліковий запис» (розділ «Ролі», відповідь 2);
- рядок «В API:» — у 29 наявних термінах і в терміні «Обліковий запис», разом 30 назв зі списку
  людини. Конфліктів назв із глосарієм агент не знайшов.

## Суперечності

Прямих суперечностей Р-117 з вимогами SRS агент не знайшов.

- REQ-F-001, REQ-F-002 і REQ-NF-021 кажуть, що запит до *екрана* без сесії веде на форму входу.
  API — не екран, тому код 401 для API цим вимогам не суперечить. Вимоги не змінено, поведінку API
  описує REQ-NF-031.
- REQ-F-003 і REQ-F-005 («немає доступу» без зміни стану) узгоджуються з 403 у REQ-NF-031.
- REQ-NF-014 (один процес) не змінено: те, що API працює в тому самому процесі, записано в REQ-NF-031
  і п. 2.5.

## Що агент не вирішував і передає людині

1. **Задум.** `spec/concept.md`, аспект «Де»: «доступ через веб-інтерфейс у браузері». Прямої
   суперечності немає, бо слова «лише» там немає. Проте задум є першоджерелом меж (п. 1.4), а REST
   API в ньому не згадано. Агент задум не змінював; за прецедентом Р-14 зміну задуму робить людина
   окремим комітом.
2. **Рядок Р-39 у додатку В.2** («…без публічного API») лишився як історичне формулювання рішення.
   Позначку «змінено Р-117» агент не додавав, бо такої зміни немає в промпті (закрито після
   перегляду, див. нижче).
3. **Що лишається контракту.** Р-117 не визначає:
   - формат чисел у JSON (на екранах — кома і два знаки, Д.11);
   - значення перелічень: статуси, спосіб запуску, вид події, роль;
   - назви для термінів без рядка «В API:»: «Подія «зміна ціни»», «з'явився», «зник», «База
     стрічки», «Лічильник відсутностей», «Ознака «зник»», «Деактивація», «Перев'язка», «Дата
     останнього оновлення», «Статус запуску», «Попередження», «Кількість розібраних позицій»,
     «Остання відома ціна», «Ціна, придатна до порівняння» та інші;
   - текст помилки для 401.

   Агент нічого з цього не задавав.
4. **REQ-NF-009** (час відповіді до 2 с) стосується лише екранів; на API Р-117 його не поширює.
5. **Тікети.** Для REQ-NF-031 і BDD-068 тікета немає; `docs/tickets.md` і колонку «Тікет» агент не
   змінював.
6. **REQ-NF-002** вимагає ручної перевірки в браузерах лише для сценаріїв вебінтерфейсу; BDD-068
   стосується API, тому під цю перевірку не підпадає.
