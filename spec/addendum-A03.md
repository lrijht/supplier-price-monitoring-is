# Адендум A-03 до специфікації вимог

| Поле | Значення |
|---|---|
| Номер | A-03 |
| Дата | 2026-10-28 |
| Базова версія | `spec/srs.md` 1.7 (базова 1.5 з адендумами A-01 і A-02), коміт `8394810` |
| Нова версія | `spec/srs.md` 1.8 |
| Рішення | Р-117 (повне формулювання — у розділі 1 цього адендума) |

## 1. Причина

Лабораторна робота 4 — проєктування REST API за специфікацією. SRS 1.7 програмного інтерфейсу не
передбачає: п. 3.1.4 — «не застосовно», а п. 2.7 відносить «публічний програмний інтерфейс (API)
для інших систем» до того, що не входить у поточну версію (Р-39). Без зміни вимог контракт API
суперечив би SRS. Людина ухвалила рішення Р-117, і цей адендум вносить його у вимоги.

Рішення Р-117 (2026-10-28):

- система надає REST API з префіксом `/api/v1`, формат даних — JSON; API обслуговує той самий
  процес, що й вебінтерфейс (REQ-NF-014);
- вебінтерфейс не змінюється: сторінки, як і раніше, формуються на сервері; REQ-NF-015 не змінено;
- API дає ті самі функції, що й екрани та дії вимог REQ-F-001…REQ-F-069; нових бізнес-функцій немає;
- вхід через API відкриває ту саму сесію, що й форма входу; 8 годин бездіяльності (REQ-NF-021)
  діють так само. Ключів і токенів доступу для зовнішніх систем немає, вебхуків немає — це
  лишається поза межами;
- права в API такі самі, як у ролей (REQ-F-003, REQ-F-004). Запит без сесії отримує 401 (а не
  перехід на форму входу, як для екранів); запит менеджера до операції адміністратора — 403 з
  повідомленням «немає доступу», стан системи не змінюється (REQ-F-005);
- створення облікових записів через API немає, лише командою початкового налаштування (REQ-F-006);
  видалення записів через API теж немає, лише деактивація (REQ-F-010);
- назви полів і ресурсів — англійською, тексти помилок — українською (REQ-NF-001). Дати в API — у
  форматі ISO 8601 (РРРР-ММ-ДД; час — зі зсувом київського часу); REQ-NF-030 стосується показу на
  екранах;
- помилки мають один формат, його описує контракт;
- контракт API — файл `spec/openapi.yaml` (створюється наступним кроком). Після API-GATE він
  змінюється лише адендумом, як і SRS.

Під час оформлення адендума людина уточнила (2026-10-28):

- п. 2.1: окремої зовнішньої сторони для API немає; менеджер і адміністратор працюють через
  вебінтерфейс у браузері або через REST API;
- для назви «обліковий запис → account» у глосарії додано новий термін «Обліковий запис»: такого
  терміна раніше не було;
- назви в рядках «В API:» глосарія записано так, як їх дала людина. У контракті поля пишуться в
  snake_case (`supplier_item`, `catalog_url`), шляхи — множиною в kebab-case (`/supplier-items`),
  значення перелічень — у snake_case (`unit_mismatch`); точне написання задає контракт;
- адміністративна операція в BDD-068 — зміна порогу сповіщень.

Після перегляду першої редакції адендума людина дала ще дві правки (2026-10-28):

- у п. 3.1.4 записано, що API призначений для тих самих користувачів і ролей, що й вебінтерфейс,
  а інтеграцій з іншими системами (ключі й токени доступу, вебхуки) немає;
- у рядку Р-39 додатка В.2 позначено, що частину «без публічного API» змінено рішенням Р-117.

## 2. Перелік змін у `spec/srs.md`

- Версія 1.8; рядок в «Історії змін»; шапка документа — джерело рішення Р-117.
- П. 1.4 — посилання на адендум A-03 і на контракт `spec/openapi.yaml`; п. 1.5 — рішення
  Р-01…Р-117.
- П. 2.1 — менеджер і адміністратор працюють через вебінтерфейс або через REST API.
- П. 2.2 — речення про те, що ті самі функції доступні через REST API (REQ-NF-031).
- П. 2.4 — доступ через вебінтерфейс і через REST API.
- П. 2.5 — один процес обслуговує вебінтерфейс, REST API і планувальник; сторінки вебінтерфейсу
  формуються на сервері.
- П. 2.7 — замість рядка «мобільна адаптація, публічний програмний інтерфейс (API) для інших
  систем (Р-39)» — «мобільна адаптація (Р-39)» і новий рядок «ключі й токени доступу до REST API
  для зовнішніх систем, вебхуки (Р-117)».
- П. 3.1.4 — замість «не застосовно» — опис REST API і контракту; речення «API призначений для
  тих самих користувачів і ролей, що й вебінтерфейс; інтеграцій з іншими системами (ключі й
  токени доступу, вебхуки) немає (п. 2.7)»; нова вимога REQ-NF-031.
- Додаток А — BDD-068 у розділі А.6.
- Додаток В — речення про джерело рішення Р-117; рядок Р-117 у В.2; у кінці формулювання рядка
  Р-39 — «(частину «без публічного API» змінено рішенням Р-117, адендум A-03)». Колонку «Вимоги» нового рядка
  згенеровано з колонки «Джерело» вимог; для наявних рядків вона не змінилася.

## 3. Вплив на вимоги

**Змінено:** формулювання, джерела і критерії наявних вимог не змінено. Р-117 змінює лише розділи
2.1, 2.4, 2.5, 2.7 і 3.1.4.

**Додано:**

| Вимога | Зміст | Рішення |
|---|---|---|
| REQ-NF-031 | REST API: префікс `/api/v1`, JSON, той самий процес; ті самі функції, що й екрани та дії REQ-F-001…REQ-F-069, без створення облікових записів і видалення; та сама сесія і строк її дії; права ролей, 401 без сесії, 403 «немає доступу» для менеджера без зміни стану; назви англійською, тексти помилок українською; одна модель помилок; дати ISO 8601. Критерій — операції в контракті `spec/openapi.yaml`, коди 401 і 403, строк сесії, модель помилок, приклади дат | Р-117 |

**Сценарії використання:** не змінено. Нових сценаріїв немає.

**Сценарії BDD:** додано BDD-068; наявні сценарії не змінено.

| Сценарій | Зміст | Вимоги |
|---|---|---|
| BDD-068 | Доступ до API за ролями: запит без сесії — 401; менеджер, що змінює поріг, — 403 «немає доступу», поріг не змінився; адміністратор — 200, поріг змінено | REQ-NF-031, REQ-F-003, REQ-F-005 |

Нічого не вилучено; ID наявних вимог і сценаріїв не змінено. Разом у версії 1.8: 69 REQ-F,
31 REQ-NF, 68 BDD, 16 UC.

## 4. Вплив на матрицю трасування

- Додано рядок REQ-NF-031 (джерело Р-117, BDD-068, без UC). Колонка «Тікет» для нього порожня:
  тікета ще немає.
- Колонка «BDD»: BDD-068 додано до REQ-F-003 і REQ-F-005.
- У підсумку — 31 нефункціональна вимога і 68 сценаріїв BDD.
- Матрицю перегенеровано з `spec/srs.md`; колонку «Тікет» наявних вимог перенесено з чинної матриці
  без змін.

## 5. Вплив на глосарій

- У вступі — пояснення рядка «В API:» і правила написання назв у контракті.
- Додано терміни «REST API», «Контракт API», «Модель помилок API» і «Обліковий запис».
- Рядок «В API:» додано до термінів: «Постачальник» (supplier), «Матеріал» (material), «Позиція
  постачальника» (supplier item), «Артикул постачальника» (sku), «Прив'язка» (link), «Непов'язана
  позиція» (unlinked item), «Позиція, що потребує уваги» (attention item), «Одиниця виміру» (unit),
  «Позначка «одиниця не збігається»» (unit_mismatch), «Ціна дня» (daily price), «Застаріла ціна»
  (stale), «Загальний список порівняння» (comparison list), «Порівняння матеріалу» (material
  comparison), «Найдешевший постачальник» (cheapest supplier), «Різниця з найдешевшим» (difference
  from cheapest), «Екран історії матеріалу» (price history), «Стрічка змін» (feed), «Подія»
  (event), «Поріг сповіщень» (notification threshold), «Запуск» (run), «Спосіб запуску» (trigger),
  «Журнал оновлень» (run log), «Статус постачальника (у запуску)» (supplier run status), «Прийняття
  нового обсягу» (volume acceptance), «База обсягу» (volume baseline), «Налаштування» (settings),
  «Розбирач» (parser), «Адреса каталогу» (catalog url), «Стан оновлення постачальників» (supplier
  update status), «Обліковий запис» (account).
