| Поле | Значення |
|---|---|
| Лабораторна | 4, крок 2 — проєктування API на рівні ресурсів |
| Базова специфікація | `spec/srs.md` 1.8 (адендум A-03, рішення Р-117), `spec/glossary.md`, `spec/traceability.md` |
| Статус | чернетка; `spec/openapi.yaml` ще не створено |

Документ готує контракт API (REQ-NF-031). Нових функцій він не вводить. Усе, що SRS для API не
визначає, винесено в розділ 5 «Прогалини» як питання з варіантами. Чернетка використовує один із
варіантів лише там, де без нього таблицю не заповнити, і позначає таке місце посиланням на прогалину
(ПА-n).

## 0. Загальні правила

- Префікс усіх адрес — `/api/v1`; у таблицях його пропущено. Дані — JSON (REQ-NF-031).
- Шляхи — множиною в kebab-case, поля й значення перелічень — у snake_case (глосарій, вступ).
- Назви ресурсів беруться з рядків «В API:» глосарія. Назви полів, яких у глосарії немає, позначено
  `*`: їх запропонував агент, і їх ще треба затвердити (ПА-4).
- Дати — `РРРР-ММ-ДД`, дата й час — ISO 8601 зі зсувом київського часу, наприклад
  `2026-10-05T03:30:05+03:00` (REQ-NF-031).
- Сесія — та сама, що й у вебінтерфейсі (REQ-NF-031). Вона відкривається ресурсом сесії і
  завершується після 8 годин бездіяльності (REQ-NF-021). Ключів і токенів немає.
- Методу DELETE в API немає (REQ-F-010, REQ-NF-031). Постачальника й матеріал виводять з ужитку
  через `PATCH` з `active: false`, повертають через `active: true`.
- Списки, для яких REQ-F-057 задає розбиття, віддаються по 50 записів. Номер сторінки задає параметр
  `page`. Розміру сторінки і параметра сортування немає: порядок фіксований (REQ-F-057).
- Права — як у ролей (REQ-F-003, REQ-F-004). Колонка «Роль» у розділі 3: «обидві» — менеджер і
  адміністратор, «адмін» — лише адміністратор.
- Перевірки йдуть у такому порядку: сесія (401) → роль (403) → існування ресурсу (404) → вміст
  запиту (422) → стан системи (409). Тож менеджер на адміністративній адресі завжди отримує 403, а
  не 404 — навіть якщо такого ідентифікатора немає. Це вимога REQ-F-005: «немає доступу», а не
  «не знайдено».

## 1. Функціональні вимоги: операція API чи внутрішня поведінка

Значення колонки «Вид»:
- **операція API** — вимога задає екран, дію користувача або вміст відповіді, тому в API для неї є
  операція;
- **внутрішня поведінка** — вимога задає те, що система робить сама (запуск, розбір, правила
  подій і обчислень). Окремої операції немає, але результат видно у відповідях названих операцій;
- **поза API** — дію виконують не через API.

## 2. Модель ресурсів

Діаграма зв'язків — `docs/api/resources.mmd`.

| Ресурс | Термін глосарію | URI | Основні поля | Зв'язки |
|---|---|---|---|---|
| сесія | — (терміна немає, ПА-3) | `/sessions`, `/sessions/current` | `account` (`login*`, `role*`) | належить обліковому запису |
| обліковий запис | Обліковий запис (account) | окремої адреси немає; вкладений у сесію | `login*`, `role*` | — |
| постачальник | Постачальник (supplier) | `/suppliers`, `/suppliers/{supplier_id}` | `id*`, `name*`, `catalog_url`, `parser`, `active*`, `last_update_date*` | має один розбирач; має позиції; має статуси в запусках |
| розбирач | Розбирач (parser); Список наявних розбирачів | `/parsers` | `parser` | обирається для постачальника |
| матеріал | Матеріал (material) | `/materials`, `/materials/{material_id}` | `id*`, `name*`, `unit`, `active*`, `linked_items_count*` | має прив'язки |
| позиція постачальника | Позиція постачальника (supplier item) | власної адреси немає (ПА-1); вкладена в прив'язку, непов'язану позицію й позицію, що потребує уваги | `id*`, `supplier`, `sku`, `name*`, `unit`, `last_seen_date*` | належить постачальнику; має не більше однієї прив'язки |
| прив'язка | Прив'язка (link) | `/links`, `/links/{link_id}`, `/materials/{material_id}/links` | `id*`, `supplier_item`, `material` | з'єднує одну позицію з одним матеріалом |
| непов'язана позиція | Непов'язана позиція (unlinked item) | `/unlinked-items` | поля позиції + `supplier.active*` | вибірка позицій без прив'язки |
| позиція, що потребує уваги | Позиція, що потребує уваги (attention item) | `/attention-items` | `supplier_item` (одиниця на сторінці — `supplier_item.unit`), `material` (одиниця — `material.unit`), `last_unit_mismatch_date*`, `supplier.active*` | вибірка прив'язаних позицій |
| ціна дня | Ціна дня (daily price) | власної адреси немає (ПА-22); вкладена в порівняння та історію | `price*`, `date*`, `unit_mismatch` | належить позиції й матеріалу |
| загальний список порівняння | Загальний список порівняння (comparison list) | `/material-comparisons` (ПА-17) | рядки: `material`, `cheapest_supplier` або `null`, `price*` або `null` | рядок на кожен активний матеріал |
| порівняння матеріалу | Порівняння матеріалу (material comparison) | `/material-comparisons/{material_id}` | `material`; рядки: `supplier`, `daily_price` або `null`, `stale`, `cheapest*`, `difference_from_cheapest` (`percent*`, `amount*`) або `null` | будується з цін дня прив'язаних позицій |
| історія матеріалу | Екран історії матеріалу (price history) | `/price-histories/{material_id}` (ПА-17) | `material`, `period*`; рядки: `date*`, `supplier`, `price*`, `unit_mismatch`, `effective_at_period_start*` | будується з цін дня матеріалу |
| подія (стрічка) | Подія (event); Стрічка змін (feed) | `/events` | `id*`, `kind*`, `date*`, `created_at*`, `material`, `supplier`, `old_price*`, `new_price*`, `change_percent*`, `price*` | належить матеріалу й постачальнику |
| стан оновлення постачальників | Стан оновлення постачальників (supplier update status) | `/supplier-update-statuses` | рядки: `supplier`, `last_update_date*` | рядок на кожного активного постачальника |
| налаштування | Налаштування (settings); Поріг сповіщень (notification threshold) | `/settings` | `update_time*`, `notification_threshold` | одне на систему |
| запуск | Запуск (run); Спосіб запуску (trigger) | `/runs`, `/runs/{run_id}` | `id*`, `trigger`, `started_at*`, `finished_at*`, `started_by*`, `status*`, `supplier_run_statuses` | має статус кожного постачальника |
| статус постачальника в запуску | Статус постачальника (у запуску) (supplier run status) | власної адреси немає; вкладений у запуск | `supplier`, `status*`, `parsed_items_count*`, `error_reason*`, `warnings*`, `volume_acceptance_available*` | належить запуску й постачальнику |
| прийняття нового обсягу | Прийняття нового обсягу (volume acceptance); База обсягу (volume baseline) | `/volume-acceptances` | `id*`, `run_id*`, `supplier`, `accepted_by*`, `accepted_at*`, `volume_baseline` | посилається на запуск і постачальника |
| журнал оновлень | Журнал оновлень (run log) | `/run-log` (ПА-16) | записи: `kind*` + запуск, запис «пропущено», запис «немає активних постачальників» або прийняття обсягу | містить запуски, інші записи й прийняття обсягу |

Вкладені посилання (`supplier`, `material`) містять `id*` і назву (`name*`). Так клієнт показує
рядок без додаткових запитів. Позиції, що потребують уваги, і непов'язані позиції додатково
отримують `supplier.active*` — для позначки «постачальник неактивний» (REQ-F-011).

### Чому так

- **Ручний запуск — `POST /runs`.** Дія створює новий запис у колекції запусків. Запуск триває до
  5 хвилин (REQ-NF-008), тому чернетка повертає 202 і адресу запуску. Варіанти — ПА-13.
- **Прийняття нового обсягу — `POST /volume-acceptances` з тілом `{run_id, supplier_id}`.**
  Прийняття — окремий запис журналу з постачальником, логіном, часом і прийнятою кількістю
  (словник даних, Д.7а). Тому дія створює ресурс у колекції, і дієслова в адресі не потрібно.
  `run_id` потрібен тому, що кнопка належить рядку постачальника в записі конкретного запуску. Якщо
  між переглядом і запитом цей запуск перестав бути останнім для постачальника, сервер відповідає
  409 (REQ-F-031: пізніший статус прибирає кнопку). Відкинуті варіанти:
  - `PATCH /suppliers/{supplier_id}` з `volume_baseline`. Він дозволив би задати довільне число,
    а це нова функція: за REQ-F-031 базою стає лише кількість позицій цього запуску. До того ж
    він не створює запису журналу.
  - `POST /runs/{run_id}/supplier-run-statuses/{supplier_id}/volume-acceptance`. Це вкладений
    ресурс в однині, і прийняття не видно окремою колекцією.
- **Прив'язка — окрема колекція `/links`.** `POST /links` лише створює прив'язку. Для позиції, вже
  прив'язаної до іншого матеріалу, він відповідає 409: REQ-F-013 вимагає, щоб без зняття першої
  прив'язки другу створити не можна було. Перев'язка — окрема дія `PATCH /links/{link_id}`
  (REQ-F-015, REQ-F-069). Зняття прив'язки без DELETE — ПА-1.
- **Непов'язані позиції й позиції, що потребують уваги — окремі колекції лише для читання.**
  Глосарій дає їм окремі назви в API, і кожна має свій порядок і поля (REQ-F-012, REQ-F-068).
  Варіант `/supplier-items?linked=false` відкинуто: він вимагав би назви для фільтрів, яких
  у глосарії немає.
- **Стрічка змін — `/events`.** Стрічка — це колекція подій, а шлях за правилом — множиною.
- **Ціни дня окремою колекцією не віддаються.** Жоден екран не показує ціни дня без обробки, тому
  колекція `/daily-prices` була б новою функцією (REQ-NF-031). Питання — ПА-22.
- **Без деталей реалізації.** Внутрішній стан у відповідях не показано: база стрічки, лічильник
  відсутностей, ознака «зник», знімок запуску. Базу обсягу видно лише у відповіді на прийняття
  обсягу (ПА-21).

## 4. Модель помилок (чернетка)

Формат — `application/problem+json` (RFC 9457). Кожна відповідь з кодом 4xx чи 5xx має такий
вигляд (REQ-NF-031: одна модель помилок).

| Поле | Тип | Зміст |
|---|---|---|
| `type` | рядок (URI) | тип проблеми; значення — ПА-10 |
| `title` | рядок | короткий опис типу українською, однаковий для одного `code` |
| `status` | ціле | код HTTP, той самий, що в рядку статусу |
| `detail` | рядок | пояснення цього випадку українською (REQ-NF-031) |
| `code` | рядок | наше поле: машинний код помилки з таблиці нижче, snake_case |
| `errors` | масив | лише для `validation_failed` і помилок полів: `{ "field": …, "code": …, "detail": … }` |

Приклад (403, BDD-068):

```json
{
  "type": "about:blank",
  "title": "Немає доступу",
  "status": 403,
  "detail": "немає доступу",
  "code": "forbidden"
}
```

Приклад (422, REQ-F-019; тексти й значення `type` — чернетка, ПА-9, ПА-10):

```json
{
  "type": "about:blank",
  "title": "Некоректні дані",
  "status": 422,
  "detail": "Запит містить некоректні значення.",
  "code": "validation_failed",
  "errors": [
    { "field": "notification_threshold", "code": "notification_threshold_out_of_range", "detail": "…" },
    { "field": "update_time", "code": "update_time_invalid", "detail": "…" }
  ]
}
```

Правила:
- 422 — запит некоректний сам собою: формат, обов'язковість, межі, невідомий розбирач, посилання
  на неіснуючий ідентифікатор у тілі. Поле `errors` є завжди.
- 409 — запит коректний, але суперечить поточному стану системи; після зміни стану той самий запит
  може пройти. Для конфлікту, пов'язаного з полем (`supplier_name_taken`, `material_name_taken`,
  `unit_locked`), поле `errors` теж є.
- Помилка не змінює стану системи. Виняток — ПА-12, варіант Б.

## 5. Прогалини

Усе, що SRS 1.8 і глосарій для API не визначають. Агент нічого з цього не вирішував. У таблицях
розділів 2–4 до вирішення стоїть позначка ПА-n.

**ПА-1. Зняття прив'язки без DELETE.** REQ-F-010 прямо каже, що зняття прив'язки не є видаленням,
тож DELETE для нього SRS не забороняє. Проте правило проєктування «DELETE нема ніде» його виключає.
Варіанти:
- А. `DELETE /links/{link_id}` — звичайний для REST спосіб. Суперечить лише правилу проєктування.
  Рецензент може прочитати критерій REQ-NF-031 («операцій … видалення записів у контракті немає»)
  буквально.
- Б. `PATCH /supplier-items/{supplier_item_id}` з тілом `{"link": null}`. Тоді позиція
  постачальника отримує власну адресу, а `/supplier-items/{supplier_item_id}` — ще й `GET`.
- В. Прив'язка — підресурс позиції в однині: `/supplier-items/{supplier_item_id}/link`, де `POST`
  прив'язує, `PATCH` перев'язує, а знімає… знову DELETE або PATCH з `null`. Шлях в однині порушує
  правило «множиною».

**ПА-2. Вихід без DELETE.** Сесія — не запис системи в сенсі REQ-F-010, тож DELETE для неї SRS не
забороняє. Варіанти:
- А. `DELETE /sessions/current`;
- Б. `PATCH /sessions/current` з `{"active": false}` — за зразком деактивації;
- В. `POST /sessions/current/logout` — дієслово в адресі.

**ПА-3. Терміна «сесія» в глосарії немає.** Слово вживається в REQ-NF-021 і REQ-NF-031, але
окремого терміна з рядком «В API:» немає, а правило проєктування дозволяє назви лише з глосарію.
Варіанти:
- А. Додати термін «Сесія» (session) до глосарію адендумом.
- Б. Назвати ресурс через наявний термін «Обліковий запис» (account). Це гірше: вхід створює сесію,
  а не обліковий запис.

**ПА-4. Назви полів, яких немає в глосарії.** Рядки «В API:» є лише для понять. Атрибути назв не
мають: назва, найменування, активний, ціна, дата тощо. Глосарій каже, що точне написання задає
контракт, а правило проєктування — що назви беруться лише з глосарію. Агент позначив `*` усі
запропоновані назви:

| Поняття SRS | Запропоновано | Примітка |
|---|---|---|
| ідентифікатор у шляху і полі | `id`, `supplier_id`, `material_id`, `link_id`, `run_id`, `supplier_item_id` | форма значення — ПА-18 |
| назва постачальника; найменування матеріалу і позиції | `name` | у SRS два слова, в API одне |
| ознака «активний» | `active` | — |
| дата останнього оновлення | `last_update_date` | — |
| кількість прив'язаних позицій | `linked_items_count` | — |
| дата, коли позицію бачили востаннє | `last_seen_date` | — |
| дата останньої ціни дня з позначкою | `last_unit_mismatch_date` | екран «позиції, що потребують уваги» |
| ціна; дата ціни | `price`, `date` | — |
| виділений найдешевший у рядку порівняння | `cheapest` | глосарій дає `cheapest supplier` лише для поняття |
| різниця у % і грн | `difference_from_cheapest.percent`, `.amount` | — |
| позначка «чинна на початок періоду» | `effective_at_period_start` | — |
| період історії | `period` | — |
| вид події; дата й час створення | `kind`, `created_at` | `type` зайнято в моделі помилок |
| стара ціна, нова ціна, зміна у % | `old_price`, `new_price`, `change_percent` | — |
| час оновлення | `update_time` | — |
| час початку й завершення; логін запустившого; загальний статус | `started_at`, `finished_at`, `started_by`, `status` | — |
| кількість розібраних позицій; причина помилки; попередження | `parsed_items_count`, `error_reason`, `warnings` | — |
| є кнопка «прийняти новий обсяг» | `volume_acceptance_available` | — |
| хто й коли прийняв обсяг | `accepted_by`, `accepted_at` | — |
| логін, пароль, роль | `login`, `password`, `role` | — |

Варіанти:
- А. Людина затверджує таблицю, і назви потрапляють у контракт.
- Б. Адендум до глосарію з рядками «В API:» для цих атрибутів.

**ПА-5. Значення перелічень.** Глосарій називає поняття, але не їхні значення. Кандидати:

| Перелік | Значення в SRS | Кандидати |
|---|---|---|
| роль | менеджер, адміністратор | `manager`, `admin` / `administrator` |
| спосіб запуску (`trigger`) | за розкладом, вручну, доганяння | `scheduled`, `manual`, `catch_up` |
| загальний статус запуску | успіх, частково, помилка, перервано | `success`, `partial`, `error`, `interrupted` |
| статус постачальника в запуску | успіх, частково, помилка; стан «не завершено» | ті самі + `not_finished` / `incomplete` |
| вид події | зміна ціни, з'явився, зник | `price_change`, `appeared`, `disappeared` |
| період історії | 7 днів, 30 днів, весь період | `7d`, `30d`, `all` / `days_7`, `days_30`, `all` |
| вид запису журналу | запуск, «пропущено», «немає активних постачальників», прийняття обсягу | `run`, `skipped`, `no_active_suppliers`, `volume_acceptance` |
| привід запису «немає активних постачальників» | налаштований час, кнопка ручного запуску (Д.7а) | `scheduled`, `manual` |
| вид попередження | одиниця не збігається, повторний артикул, рядок без артикула чи з помилкою розбору, нульова чи від'ємна ціна | `unit_mismatch`, `duplicate_sku`, `unparsed_row`, `non_positive_price` |
| причина помилки постачальника | сторінка недоступна; перевищено час очікування N с; сторінку не розібрано; текст збою запису | перелік + `timeout_seconds`, або лише текст |

Окреме питання — чи віддавати текст українською поруч зі значенням переліку (наприклад, причину
помилки так, як її показує журнал).

**ПА-6. Формат чисел.** На екранах — кома, два знаки для цін, один для відсотків, «+» для додатних
(Д.11). Для JSON SRS нічого не задає. Варіанти для цін і різниці:
- А. Число JSON (`1250.5`). Точність десяткових дробів залежить від клієнта.
- Б. Рядок з крапкою і фіксованою кількістю знаків (`"1250.50"`).
- В. Ціле число копійок (`125050`).

Для відсотків (`change_percent`, `difference_from_cheapest.percent`) окремі питання:
- віддавати значення, округлене до 0,1, як на екрані, чи точне;
- чи потрібен знак: для числа він зайвий.

Для порогу (`notification_threshold`): REQ-F-019 вимагає, щоб введення приймало і кому, і крапку.
- А. Число JSON (`0.5`): кома в JSON неможлива, тож вимога стосується лише форми вебінтерфейсу.
- Б. Рядок, що приймає `"0,5"` і `"0.5"`.

**ПА-7. Відсутні значення.** На екранах вони показуються як «—», «ще не оновлювався», «ціни ще
немає», а в перерваного запуску час завершення — «—». Варіанти:
- А. `null`;
- Б. поле відсутнє;
- В. окреме поле стану.

Чернетка використовує `null`.

**ПА-8. Формат часу оновлення.** REQ-NF-031 задає формат дат і дат із часом, а часу доби не задає.
Варіанти: `"03:30"` (ISO 8601, ГГ:ХХ, як на екрані) або `"03:30:00"`. У будь-якому разі `"3:30"`
відхиляється, як у REQ-F-019.

**ПА-9. Тексти помилок.** SRS дає дослівно лише чотири тексти:
- «немає доступу»;
- «одиницю не можна змінити: є ціни або прив'язки»;
- «оновлення вже триває»;
- «матеріал деактивовано».

Ще «немає активних постачальників» — текст запису журналу. Не визначено тексти:
- для 401: без сесії і неправильний вхід;
- для 404, 405 і 400;
- для 422 за кожним полем;
- для 409 у REQ-F-007, REQ-F-008, REQ-F-013, REQ-F-014, REQ-F-048, REQ-F-050 і REQ-F-031. Для
  REQ-F-014, REQ-F-048 і REQ-F-050 SRS задає лише зміст.

Не визначено й `title` для кожного `code`. Варіанти:
- А. Агент пропонує тексти в контракті, людина затверджує на API-GATE.
- Б. Тексти задає адендум до SRS.

**ПА-10. Значення `type` і мова `title`.** Варіанти для `type`:
- А. `about:blank` для всіх: тип визначає `code`.
- Б. Окремий URI на кожен `code`, наприклад `/api/v1/problems/run-in-progress`. Тоді він має
  відкриватися, або треба вирішити, що не мусить.

Чернетка вважає `title` українським текстом, бо REQ-NF-031 вимагає тексти помилок українською. Це
теж треба підтвердити.

**ПА-11. Порівняння деактивованого матеріалу.** На екрані замість таблиці — «матеріал деактивовано»
(REQ-F-049). Варіанти відповіді API:
- А. 200 з `material.active: false` і без рядків.
- Б. 409 `material_deactivated` з detail «матеріал деактивовано».
- В. 404 — не підходить: матеріал існує, і повідомлення має бути саме «матеріал деактивовано».

**ПА-12. Ручний запуск без активних постачальників.** Запуску немає, але журнал отримує запис
«немає активних постачальників» (REQ-F-063). Варіанти:
- А. 201 з цим записом журналу.
- Б. 409 `no_active_suppliers` з detail «немає активних постачальників». Запис журналу при цьому
  створюється, тож помилка змінює стан. Це суперечить правилу розділу 4.
- В. 200 без тіла запису.

**ПА-13. Відповідь `POST /runs` і запуск, що триває.** Запуск асинхронний: до 5 хвилин
(REQ-NF-008). Варіанти відповіді: 202 з `Location` (чернетка), 201 з запуском або 200.

Окреме питання — що показують `GET /runs/{run_id}` і `GET /run-log`, поки запуск триває. Перелік
загальних статусів (REQ-F-032) такого стану не має. Варіанти:
- А. `status: null` і `finished_at: null`;
- Б. нове значення переліку на кшталт `in_progress`. Тоді його треба внести в SRS адендумом.

Чи видно запуск, що триває, у вебжурналі, SRS теж не каже.

**ПА-14. Списки вибору для менеджера.** Менеджер обирає матеріал на екрані історії, зокрема
деактивований з опцією «показати неактивні» (REQ-F-040, REQ-F-049). Він також фільтрує стрічку за
матеріалом і постачальником, зокрема деактивованим (REQ-F-011, REQ-F-058). У вебінтерфейсі ці
списки — частина екранів менеджера. В API `GET /materials` і `GET /suppliers` — адміністративні
операції (екрани «матеріали» і «постачальники», REQ-NF-003, REQ-F-069), а `GET /material-comparisons`
віддає лише активні матеріали. Тому з чернетки менеджер не може дізнатися ідентифікатор
деактивованого матеріалу. Варіанти:
- А. `GET /materials` і `GET /suppliers` доступні обом ролям: менеджеру — лише ідентифікатор, назва
  й `active`.
- Б. Окремі ресурси списків вибору. Назв для них у глосарії немає.
- В. Параметр на кшталт `include_inactive` у `GET /material-comparisons`. Це змішує список вибору з
  екраном порівняння.

**ПА-15. Сторінки.** Не визначено:
- з якого номера починається `page` (чернетка — з 1);
- що віддає номер за межами (порожній список, 404 чи 422);
- які відомості про сторінки є у відповіді: загальна кількість записів, кількість сторінок, номер
  поточної, посилання на сусідні сторінки (у тілі чи в заголовку `Link`);
- як поводитися з невідомими параметрами запиту і з полями лише для читання в тілі PATCH
  (`linked_items_count`, `last_update_date`): ігнорувати чи відповідати 422.

**ПА-16. Назва журналу оновлень і його записів.** Правило «шляхи множиною» не дає назви для журналу:
`run log` — одне ціле. Терміна для запису журналу, запису «пропущено» і запису «немає активних
постачальників» у глосарії немає. Варіанти:
- А. `/run-log` (чернетка) — однина, порушує правило.
- Б. `/run-log-entries` — назва «entry» не з глосарію.
- В. Лише `/runs` і `/volume-acceptances`, без загального журналу. Тоді REQ-F-057 (50 записів на
  сторінку для журналу загалом) і показ записів «пропущено» потребують окремого рішення.

**ПА-17. Шляхи порівняння й історії.** Чернетка:
- `/material-comparisons` — колекція рядків загального списку порівняння;
- `/material-comparisons/{material_id}` — порівняння одного матеріалу;
- `/price-histories/{material_id}` — історія матеріалу. Слово «history» у множині незвичне.

Варіанти:
- А. Як у чернетці.
- Б. `/comparison-list` — назва з глосарію, але однина.
- В. Вкладені шляхи `/materials/{material_id}/comparison` і `/materials/{material_id}/price-history`.
  Вони однина, і під `/materials` опиняються операції обох ролей, а сам `/materials` —
  адміністративний.

**ПА-18. Форма ідентифікаторів.** За п. 3.8 SRS ідентифікатори — рішення проєктування. Варіанти:
ціле число, непрозорий рядок (наприклад, UUID). Для позиції постачальника можливий і природний ключ
«постачальник + артикул». Артикул може містити пробіли й інші символи («А 3»), тож у шляху його
довелося б кодувати.

**ПА-19. Відомості про поточну сесію.** Клієнтові API зручно знати свій логін і роль, щоб не
показувати адміністративні дії менеджерові. Варіанти:
- А. Лише у відповіді `POST /sessions` (чернетка).
- Б. Ще й `GET /sessions/current`. Це не екран і не дія вебінтерфейсу. Чи не буде це новою функцією
  за REQ-NF-031?

Окремо: логін звіряється без урахування регістру (REQ-F-001). Яким віддавати логін — як збережено
чи як введено?

**ПА-20. Захист від підробки запитів (CSRF).** API використовує cookie сесії вебінтерфейсу, тож
змінювальні запити з чужої сторінки в браузері можливі. SRS про це мовчить. ЗП-4 відносить систему
до довіреного локального середовища без HTTPS. Варіанти:
- А. Нічого не робити (ЗП-4).
- Б. Вимагати `Content-Type: application/json` для змінювальних запитів.
- В. Окремий токен. Це, можливо, суперечить «ключів і токенів немає» з Р-117.

**ПА-21. База обсягу у відповідях.** Екран «постачальники» бази обсягу не показує (REQ-F-068), тож
чернетка не віддає її в представленні постачальника. Видно її лише у відповіді на прийняття обсягу,
бо глосарій дає назву `volume baseline`. Чи так задумано, чи база обсягу має бути в представленні
постачальника?

**ПА-22. Ціни дня окремою колекцією.** Глосарій дає назву `daily price`, але жоден екран не показує
ціни дня без обробки. Чернетка вкладає їх у порівняння (`daily_price`) та історію і колекції
`/daily-prices` не має. Чи це так і задумано?

**ПА-23. Час відповіді API.** REQ-NF-009 (до 2 с на тестовому обсязі) стосується екранів. Р-117 не
поширює його на API. Відкрито з адендума A-03 (`logs/2026-10-28-addendum-a03.md`, пункт 4).
